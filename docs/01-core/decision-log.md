# Decision Log

**Role:** lightweight repo-local decision history and supersession log  
**Audience:** implementers, reviewers, and operators  
**When to read:** when a task may reopen a locked choice, when stage-scoped decisions need historical context, or when current work may conflict with prior canon  
**Authority:** durable decision record; [decision-core.md](./decision-core.md) remains the compact locked summary for day-to-day implementation

## How To Use This Log

- add a new entry instead of rewriting older decisions in place
- use `locked` for current canon that should not change without a canon update
- use `active` for the current delivery posture or in-force guidance that may later be superseded
- use `superseded` for searchable history that should no longer drive implementation
- keep titles short and searchable
- include related docs, code, or test references when they make the decision easier to preserve

## Entry Template

### YYYY-MM-DD - Short decision title

- Status: `locked | active | superseded`
- Decision: one concise statement of the decision
- Why: why the decision was made
- Impact: what later work must preserve or treat as out of scope
- Related refs: useful docs, code, tests, or PRs

### 2026-05-07 - Phones are identities; ambiguous inbound SMS escalates via the identity-resolution queue

Run lifecycle is `draft → scheduled → sending → complete → finalized` with `cancelled` reachable from `scheduled` or `sending`; a 30-day events-tail window keeps `complete` open before transitioning to `finalized`. Code merges to `main` remain blocked behind the `V` validation gate per `D-031`; this decision, the PRD, the design brief, and canon updates may land independently as docs-only changes.
- Why: independent 2025-2026 deliverability benchmarks place SendGrid shared-IP at ~61% inbox placement vs. Postmark at ~94% on the same tests; the architect's deliverability concern was data-supported. SendGrid Marketing Campaigns ($120-250/mo at AS scale) was outside the budget envelope ($240-480/yr stated). Postmark Basic 10K + 50K tiers land within budget, deliver best-in-class reputation infrastructure, and uniquely support our locked per-recipient stored-token unsubscribe model + `List-Unsubscribe` header customization natively (SendGrid's path required workarounds). Resend, Loops, and Customer.io were disqualified by per-stored-contact pricing at 43K contacts. Amazon SES (~$380/yr) was viable but required 4-6 weeks of IP warmup ops work; held as plan B if Postmark pricing creep at >50K/month becomes painful. Phasing was chosen so Postmark's deliverability is validated on small-volume project sends before staking the 43K-recipient newsletter on it; current Mailchimp newsletter audience is not migrated until Phase C and is audited against Salesforce `Subscribed_to_Org_Newsletter__c` + `HasOptedOutOfEmail` first. Composer-as-editor for Phase A defers the drag-and-drop builder until Phase B, when operators have proven the platform's send path.

### 2026-05-20 - Platform failure notifications via a single ops-alert sender (D-047)

- Status: `locked`
- Decision: Failures detected anywhere in the platform notify by email through one ops-alert sender that lives in the worker. The architecture has three parts:
  - **`OpsAlertSender`** (deep module at `apps/worker/src/ops-alert/sender.ts`): transport-injectable Gmail sender. Accepts either a structured `OpsAlertInput` (`{ category, dedupKey, severity, summary, categoryLabel, detail, links, firstObservedAt, occurredAt }` — generic body builder) or a pre-rendered `{ subject, bodyPlaintext, bodyHtml }` payload (legacy adapter path). Returns a discriminated union: `sent` / `skipped_cooldown` / `auth_error` / `transport_error`. Fails closed on missing credentials and on transport error — never throws into the caller, so a misconfig cannot cascade into a worker crash.
  - **`ops_alert_state` table** (`packages/db/drizzle/0062_ops_alert_state.sql`): primary key `(category, dedup_key)`, columns `last_sent_at`, `last_status`, `created_at`, `updated_at`. The sender consults this row before every send; if `last_sent_at` is within the cooldown window, the call returns `skipped_cooldown` without touching the transport. Cooldown resolution order: `OPS_ALERT_COOLDOWN_MS__<CATEGORY_UPPER>` env var → `OPS_ALERT_DEFAULT_COOLDOWN_MS` env var → hard default 3_600_000 ms (1 hour, matches `D-038`).
  - **Integration-health adapter** (refactor of `apps/worker/src/jobs/integration-health/email.ts`): the existing alerter from `D-038` is preserved as a thin adapter over `OpsAlertSender`. Its public constructor, env-var precedence (`INTEGRATION_HEALTH_ALERT_RECIPIENT` > `OPS_ALERT_RECIPIENT` > default), and the legacy subject `[AS Comms] <service> integration degraded — <status>` are byte-identical. The existing regression test passes unchanged. The adapter defaults its state repo to an in-memory no-op so wiring drift cannot break the regression path.
  - Subject format for new categories: `[AS Comms] <categoryLabel>: <summary>` (capped at 120 chars, ellipsized if longer). Body has five sections — Summary, First observed at, Identifiers, Detail, Action links — plaintext is the source of truth and HTML is mechanically derived.
  - Recipient is controlled by one env var `OPS_ALERT_RECIPIENT` (default `nico@adventurescientists.org`). When the operator team grows past one, flip the env var on the worker Railway service to `operations@adventurescientists.org` — no code change required. From-alias is `OPS_ALERT_FROM_ALIAS` (default `volunteers@adventurescientists.org`); transport reuses the existing volunteers@ Gmail OAuth — no new mailbox or Postmark wiring on the worker.
  - Cadence is per-event with cooldown only. No daily digest in Phase 1; defer that until volume proves noisy.
  - Seven dispatch sites are scoped for wiring against this foundation (none yet wired in `D-047`'s foundation PR):
    1. Worker dead-letter (`apps/worker/src/orchestration/service.ts`) — dedup key `sync_state:<service>:<scope>`.
    2. Campaign send stuck (`apps/worker/src/jobs/reconcile-stranded-campaign-runs.ts`) — dedup key `campaign_run:<runId>`.
    3. Postmark webhook dead-letter (handler from #436) — dedup key `postmark_webhook_deadletter:<digest-of-day>` (one alert per day).
    4. AI knowledge synthesis failure (`apps/worker/src/jobs/synthesize-project-knowledge/orchestrator.ts`) — dedup key `ai_knowledge_synthesis:<projectId>`.
    5. Composer outbound stuck (`apps/worker/src/jobs/sweep-pending-outbounds.ts`) — dedup key `composer_outbound:<contactId>`.
    6. Postmark sender failed (`apps/worker/src/jobs/poll-postmark-sender-status/poll.ts`) — dedup key `postmark_sender:<senderId>`.
    7. Worker stale-running stuck (`apps/worker/src/jobs/reconcile-stale-running.ts`) — dedup key `stale_running_sweeper`.
  - Explicitly out of scope: AI Draft button failures, daily-cost-cap warnings, any UI-surfaced interactive failure (the operator already sees those in real time); SMS-capture failures (re-evaluate after A2P port completes); recipient-side bounce/complaint events; a UI list of recent alerts. The `integration_health.last_alert_sent_at` column is kept where it is — `ops_alert_state` coexists with it rather than replacing it.
- Why: Until this decision, only one failure category emitted an alert — integration-health degradation, per `D-038`. Every other detection point in the worker (and the web-tier capture of composer-send failures, which flows back to the worker via the existing sweep) wrote a log line in Railway and nothing else. The runbooks all ended with "If recovery fails / Alert `nico@adventurescientists.org`", which is a manual operator step, not a platform-emitted signal. After Stage 5A shipped, the operator-trust risk shifted from "does capture work?" (now covered by `D-038`) to "do my sends, runs, and synthesis jobs actually complete?" — which had no alerting at all. Generalizing the `D-038` pattern (Gmail OAuth transport + 1-hour cooldown table + `[AS Comms]` subject prefix) was the smallest change that closed that gap; it costs one module + one additive migration + one adapter refactor and unlocks coverage of every detection point the worker already produces. Parameterizing the recipient via `OPS_ALERT_RECIPIENT` was non-optional — when operations@ is staffed, the operator handoff has to be an env-var flip on Railway, not a code change. Per-event with cooldown (vs. daily digest) was chosen for Phase 1 because the S1 surfaces (worker dead-letter, stuck broadcast runs, silent composer sends) need real-time response; the cooldown table is sufficient to prevent storm behavior. Postmark is intentionally not used as the ops-alert transport even though it's already on the worker for broadcasts (`D-045`) — keeping the architect-facing alert path on Gmail OAuth means an outage of the Postmark integration itself can still alert the architect.
- Impact:
  - New deep module `apps/worker/src/ops-alert/sender.ts` with `OpsAlertSender`, `OpsAlertInput`, `RenderedOpsAlertInput`, `OpsAlertSendInput`, `OpsAlertSendResult`, `createOpsAlertSender`.
  - New table `ops_alert_state` (`packages/db/drizzle/0062_ops_alert_state.sql`) plus Drizzle schema entry `opsAlertState` exported from `packages/db/src/schema/index.ts` and a repository on the Stage 2 bundle (`opsAlertState.getLastSentAt`, `opsAlertState.recordSent`). Additive only — no destructive changes; `integration_health.last_alert_sent_at` is preserved.
  - Worker runtime (`apps/worker/src/runtime.ts`) and orchestration tasks (`apps/worker/src/orchestration/tasks.ts`) construct the new state repository at boot and pass it into the integration-health adapter. No other dispatch sites are modified by this foundation PR.
  - Three new env vars surfaced with safe hard defaults — no Railway-side action is required to ship the foundation: `OPS_ALERT_RECIPIENT`, `OPS_ALERT_FROM_ALIAS`, `OPS_ALERT_DEFAULT_COOLDOWN_MS`. Per-category cooldown overrides via `OPS_ALERT_COOLDOWN_MS__<CATEGORY_UPPER>` if present.
  - Existing integration-health alert behavior is operator-invisible: same subject, same cooldown, same recipient unless `INTEGRATION_HEALTH_ALERT_RECIPIENT` is explicitly set.
  - Runbook footers ("If recovery fails / Alert `nico@adventurescientists.org`") will be updated alongside Brief 3's dispatch wiring to note "You may have already received an `[AS Comms]` email for this — that's expected; the platform also self-alerts."
  - `D-038` is **extended, not superseded**: integration-health alerting still owns its 1-hour cooldown semantics, its `last_alert_sent_at` column, and its existing env vars. `D-047` adds the generic plumbing the other six surfaces will use.
  - Foundation shipped in PR [#445](https://github.com/nico-kneler-as/as-comms-platform/pull/445). Briefs 2 (the four S1 dispatch sites) and 3 (the three S2 dispatch sites + runbook updates) follow.
